# マルチエージェントレビュースキル (multi-agent-review) 【試作段階】

このスキルは、1つのPR・差分に対して、ルールカテゴリ別に専任化した複数のレビューエージェントを並列に起動し、それぞれの観点から妥協なくレビューさせるための指示書です。実装を担当したエージェント自身がレビューすると評価が甘くなりがちという課題への対策として、独立したコンテキストを持つ別エージェントに、担当ルール以外を見えなくした上でレビューさせます。

**現時点はプロトタイプです。** 各エージェントの指摘を俯瞰して重複排除・矛盾解消を行う統合エージェントはまだ実装しておらず、カテゴリごとの生の指摘をそのまま提示します。採用するかどうかはユーザーが1件ずつ判断してください。

## 🎯 起動条件

- ユーザーから「マルチエージェントでレビューして」「カテゴリ別にレビューして」等、本スキルの実行を明示的に指示された場合。

## 📋 実行プロセス（手順）

### 1. レビュー対象の特定
- ユーザーの指示からレビュー対象を特定する。
  - PR番号が指定された場合: GitHub MCP（`pull_request_read`）またはローカルの`gh pr diff <PR番号>`で差分を取得する。
  - PR番号の指定が無い場合: カレントブランチと、その派生元ブランチ（通常`main`）との差分（`git diff <派生元>...HEAD`）を対象とする。派生元が不明な場合はユーザーに確認する。

### 2. カテゴリ別レビューエージェントの並列起動
- 以下5つのエージェントを、**同一メッセージ内で並列に**（`Agent`ツールを複数回、`run_in_background: false`で）起動する。全員が結果を返すまで待つ必要があるため、バックグラウンド実行は使わない。
  - `review-design-principles`
  - `review-react-rules`
  - `review-typescript-rules`
  - `review-test-rules`
  - `review-ui-rules`
- 各エージェントへのプロンプトには、手順1で取得した差分の内容（またはPR番号・対象ブランチ名などエージェント自身が差分を取得できる情報）を必ず含める。5エージェントには全く同じレビュー対象情報を渡し、担当ルールだけが異なる状態にすること。
- 各エージェントは`ReportFindings`で指摘を報告してくる。

### 3. 結果の提示（集約・重複排除は行わない）

#### レビュー対象がPRの場合: PR上のレビューコメントとして投稿する
- 各エージェントの`ReportFindings`結果を、指摘対象の`file`（パス）・`line`（行番号）に対する**PRのインラインレビューコメント**として投稿する。ユーザーがコードを見ている画面上でそのまま採否を判断できるようにするため。
  1. `pull_request_review_write`（method: `create`、`event`は指定しない）でペンディングレビューを作成する。
  2. 各指摘について`add_comment_to_pending_review`を呼ぶ。
     - `path`: 指摘対象ファイルのリポジトリルートからの相対パス
     - `line`（複数行にまたがる指摘は`startLine`/`line`）: 指摘対象の行番号
     - `side`: `RIGHT`（PRで新規追加・変更された側のコードに対する指摘のため）
     - `subjectType`: `LINE`
     - `body`: 先頭にカテゴリ名（`[design-principles]`/`[react-rules]`/`[typescript-rules]`/`[test-rules]`/`[ui-rules]`）を明記し、指摘の要約・根拠（該当ルールファイルのどの記述か）・具体的な不具合シナリオを含める
  3. 1つの指摘が複数ファイル・複数箇所にまたがる場合（例: DRY違反で重複箇所が別ファイルにある等）、該当する各箇所にそれぞれコメントを投稿し、コメント本文内で互いの箇所を参照する。
  4. 全指摘を追加し終えたら`pull_request_review_write`（method: `submit_pending`、`event`: `COMMENT`）で送信する。**`APPROVE`/`REQUEST_CHANGES`は使わない**（採用可否はユーザーが判断するため、レビュー自体はコメントに留める）。
  5. 指摘が0件のカテゴリはPR上には何も投稿しない（投稿するインラインコメントが無いため）。ただし後述のチャット上のサマリーでは「該当カテゴリの指摘なし」を明示する。
- 投稿後、チャット上には以下を提示する。この段階でも複数エージェントにまたがる重複指摘の統合・エージェント間の裁定・指摘の取捨選択は行わない。
  - 投稿したレビューのURL
  - カテゴリごとの指摘件数サマリー（0件のカテゴリも明示）

#### レビュー対象がPRでない場合（ローカルブランチ差分等）: 従来通りチャットに提示する
- 5エージェントの`ReportFindings`結果を、**カテゴリごとに分けたまま**ユーザーに提示する。この段階で以下は行わない。
  - 複数エージェントにまたがる重複指摘の統合
  - エージェント間で判断が割れた場合の裁定
  - 指摘の取捨選択（軽微だからと省略する等）
- 各カテゴリで指摘が0件だった場合も、「該当カテゴリの指摘なし」として明示する（黙って省略しない）。

#### 共通
- ユーザーが各指摘について採用するかどうかを判断する。採用された指摘の対応（実装・コミット等）は、通常のレビュー対応と同様に行う。

## 🚫 既知の限界（プロトタイプ段階の制約）

- **カテゴリ境界での重複**: design_principles（DRY/SOLID等）とreact_rules・typescript_rulesは実務上重なる場合がある。各`review-*`エージェントの定義（`.claude/agents/review-*.md`）には担当外カテゴリを指摘しない旨を明記しているが、完全な排他は保証できない。重複した指摘が出た場合は、ユーザー側で同一の指摘として扱ってよい。
- **俯瞰エージェント未実装**: 複数エージェントの指摘を横断的に確認し、矛盾がある場合のみユーザーに判断を求める統合エージェントは、本プロトタイプの評価結果を踏まえて別途実装する予定。現時点では全指摘をそのまま提示する。
- **厳格指示による偽陽性リスク**: 各エージェントには担当ルールを妥協なく適用させているため、軽微な指摘も含めて数が多くなる可能性がある。運用しながら、指摘の質（偽陽性の割合）を評価すること。
