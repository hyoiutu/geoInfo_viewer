# マルチエージェントレビュースキル (multi-agent-review) 【試作段階】

このスキルは、1つのPR・差分に対して、ルールカテゴリ別の観点を切り替えながら妥協なくレビューさせるための指示書です。実装を担当したエージェント自身がレビューすると評価が甘くなりがちという課題への対策として、独立したコンテキストを持つ別エージェントに、いま処理中の観点以外を一旦忘れさせた上でレビューさせます。

**現時点はプロトタイプです。** 指摘を俯瞰して重複排除・矛盾解消を行う統合ステップはまだ実装しておらず、カテゴリごとの生の指摘をそのまま提示します。採用するかどうかはユーザーが1件ずつ判断してください。

**設計上の経緯（当初は5エージェント並列起動だった）**: 当初は5つのカテゴリそれぞれに専任エージェントを立て、同一差分を渡して並列起動する構成だったが、同一の差分（PRの規模によっては差分だけで数万トークン）を5エージェントそれぞれに渡すと、その分だけトークン消費が単純に5倍になることが判明した。レビュー品質を支えているのは「エージェントが複数いること」自体ではなく「1つの観点だけに絞り込んで妥協なく見る」という指示の狭さであり、この効果は1エージェントが観点を順番に切り替えながら見る構成でも再現できる。加えて1エージェント構成なら、差分は最初の1回だけ読めば以降の観点でもコンテキスト上に残る（キャッシュが効く）ため、差分の再読み込みコストが発生しない。この判断により`.claude/agents/review-*.md`（5ファイル）を`review-multi-perspective.md`（1ファイル）へ統合した。

## 🎯 起動条件

- ユーザーから「マルチエージェントでレビューして」「カテゴリ別にレビューして」等、本スキルの実行を明示的に指示された場合。

## 📋 実行プロセス（手順）

### 1. レビュー対象の特定
- ユーザーの指示からレビュー対象を特定する。
  - PR番号が指定された場合: GitHub MCP（`pull_request_read`）またはローカルの`gh pr diff <PR番号>`で差分を取得する。
  - PR番号の指定が無い場合: カレントブランチと、その派生元ブランチ（通常`main`）との差分（`git diff <派生元>...HEAD`）を対象とする。派生元が不明な場合はユーザーに確認する。

### 2. 5観点レビューエージェントの起動
- `review-multi-perspective`エージェントを**1回だけ**起動する（`run_in_background: false`）。
- プロンプトには、手順1で取得した差分の内容（またはPR番号・対象ブランチ名など、エージェント自身が差分を取得できる情報）を必ず含める。このエージェントは内部で5観点（design-principles/react-rules/typescript-rules/test-rules/ui-rules）を順番に切り替えながら、同じ差分を使い回してレビューする。
- エージェントは5観点すべての処理が終わった後、`ReportFindings`で全カテゴリ分の指摘をまとめて1回報告してくる。

### 3. 結果の提示（集約・重複排除は行わない）

#### レビュー対象がPRの場合: PR上のレビューコメントとして投稿する
- `ReportFindings`結果を、指摘対象の`file`（パス）・`line`（行番号）に対する**PRのインラインレビューコメント**として投稿する。ユーザーがコードを見ている画面上でそのまま採否を判断できるようにするため。
  1. `pull_request_review_write`（method: `create`、`event`は指定しない）でペンディングレビューを作成する。
  2. 各指摘について`add_comment_to_pending_review`を呼ぶ。
     - `path`: 指摘対象ファイルのリポジトリルートからの相対パス
     - `line`（複数行にまたがる指摘は`startLine`/`line`）: 指摘対象の行番号
     - `side`: `RIGHT`（PRで新規追加・変更された側のコードに対する指摘のため）
     - `subjectType`: `LINE`
     - `body`: 先頭にカテゴリ名（`[design-principles]`/`[react-rules]`/`[typescript-rules]`/`[test-rules]`/`[ui-rules]`）を明記し、指摘の要約・根拠（該当ルールファイルのどの記述か）・具体的な不具合シナリオを含める
  3. 1つの指摘が複数ファイル・複数箇所にまたがる場合（例: DRY違反で重複箇所が別ファイルにある等）、該当する各箇所にそれぞれコメントを投稿し、コメント本文内で互いの箇所を参照する。
  4. 全指摘を追加し終えたら`pull_request_review_write`（method: `submit_pending`、`event`: `COMMENT`）で送信する。**`APPROVE`/`REQUEST_CHANGES`は使わない**（採用可否はユーザーが判断するため、レビュー自体はコメントに留める）。
  5. 指摘が0件のカテゴリはPR上には何も投稿しない（投稿するインラインコメントが無いため）。ただし後述のチャット上のサマリーでは「該当カテゴリの指摘なし」を明示する。
- 投稿後、チャット上には以下を提示する。この段階でもカテゴリをまたいだ重複指摘の統合・指摘の取捨選択は行わない。
  - 投稿したレビューのURL
  - カテゴリごとの指摘件数サマリー（0件のカテゴリも明示）

#### レビュー対象がPRでない場合（ローカルブランチ差分等）: 従来通りチャットに提示する
- `ReportFindings`結果を、**カテゴリごとに分けたまま**ユーザーに提示する。この段階で以下は行わない。
  - カテゴリをまたいだ重複指摘の統合
  - 指摘の取捨選択（軽微だからと省略する等）
- 各カテゴリで指摘が0件だった場合も、「該当カテゴリの指摘なし」として明示する（黙って省略しない）。

#### 共通
- ユーザーが各指摘について採用するかどうかを判断する。採用された指摘の対応（実装・コミット等）は、通常のレビュー対応と同様に行う。

## 🚫 既知の限界（プロトタイプ段階の制約）

- **カテゴリ境界での重複**: design_principles（DRY/SOLID等）とreact_rules・typescript_rulesは実務上重なる場合がある。`review-multi-perspective`エージェントの定義（`.claude/agents/review-multi-perspective.md`）には観点ごとに担当外を指摘しない旨・直前の観点の判断を引きずらない旨を明記しているが、完全な排他は保証できない。重複した指摘が出た場合は、ユーザー側で同一の指摘として扱ってよい。
- **観点間のアンカリングリスク**: 5観点を1エージェントが連続したコンテキストの中で順番に処理するため、前の観点で「問題なし」と判断した印象が後の観点の判断に無意識に影響する（アンカリング）リスクが、5エージェント並列構成よりは残る。エージェント定義内で「直前の観点の判断は一旦忘れる」旨を明記して緩和しているが、完全な排除は保証できない。運用しながら、5エージェント並列構成との指摘傾向の差を評価すること。
- **俯瞰統合エージェント未実装**: 複数観点の指摘を横断的に確認し、矛盾がある場合のみユーザーに判断を求める統合エージェントは、本プロトタイプの評価結果を踏まえて別途実装する予定。現時点では全指摘をそのまま提示する。
- **厳格指示による偽陽性リスク**: 各観点で担当ルールを妥協なく適用させているため、軽微な指摘も含めて数が多くなる可能性がある。運用しながら、指摘の質（偽陽性の割合）を評価すること。
